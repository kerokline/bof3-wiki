# Type-1 LZ77 payload

*Read this if you decode compressed entries (type 1).*

The LZ77 codec of EMI type-1 entries: payload layout, frame format, encoder and decoded blob header. Every EMI type-1 entry is an LZ77 stream for the scratchpad decoder at `0x80164064`. The 65
type-1 payloads decode to 21,753,944 bytes from 12,723,580 stored bytes.

Measured over all 65 entries: every payload decodes to its stated size, the encoder round-trips every decoded entry, and
the first frame that differs from retail is identified per entry.

## Payload layout

| Offset | Size | Meaning                                                       |
| -----: | ---: | ------------------------------------------------------------- |
| `0x00` |    4 | decoded size, `u32` little-endian                             |
| `0x04` |    2 | `0xFFFF` marker (`0xFFFF` in 65/65)                           |
| `0x06` |    … | control stream, terminated by a frame that starts with `0xFF` |

The stream consumes the payload exactly: the terminator is the last byte before the archive's
`0x5F` padding ([EMI](emi.md#padding)).

## Frame codec

A frame is one literal run or one back-reference into the last 2,048 decoded bytes.

| Control byte  | Frame                                                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `0x10`-`0x1F` | literal run of `0x20 - (ctrl & 0x1F)` bytes, 1-16; a count of 16 adds one length byte, so runs reach 271                                                     |
| `0xFF`        | end of stream                                                                                                                                                |
| other         | back-reference: distance `0x800 - (((ctrl & 0xE0) << 3) \| byte)`, length `(ctrl & 0x0F) + 3`; a low nibble of 15 adds one length byte, so lengths reach 273 |

Back-references may overlap their own output (`distance < length`); the forward copy reproduces
that. The 65 entries contain 633,673 literal frames (lengths 1-271) and 922,056 back-references
(lengths 3-273, distances 1-2,047).

`0x10` is ambiguous in the written format: a length-3 back-reference with high distance bits
`0xE0` collides with the 16-byte literal escape. No retail entry uses that control for a
back-reference; the encoder writes a 16-byte literal run as `0x10` followed by a `0x00` extension
byte.

## Encoder

The encoder uses a three-byte prefix index and searches back at most 2,047 bytes. It
accepts matches of 3-273 bytes, chooses the longest candidate, and chooses the nearest candidate on
a length tie. It indexes the current position before one-byte lookahead and defers the current
match only when the next match is strictly longer. Literal bytes accumulate until a match, the
271-byte limit, or end of input. Runs of 1-15 bytes use one control byte; runs of 16-271 use `0x10`,
one extension byte, and the bytes. Every frame has its own control byte; the stream ends with one
`0xFF`.

The encoder round-trips all 65 decoded entries but reproduces 0/65 retail payloads byte for byte.
First payload-byte differences range from `0x25` to `0x176` (median `0x62`). Two counterexamples
show the rule is an approximation: `BPLD012#7` output 93 has retail `3@92` where
longest-match-nearest gives `3@64`; `BRTU467#7` output 138 defers a `9@23` match to take `8@23` at
139, so the defer rule is not "only when strictly longer".

## Decoded blob

The decoded bytes open with a fixed-shape header, identical across all 65 entries.

| Offset |   Size | Meaning                                                     |
| -----: | -----: | ----------------------------------------------------------- |
| `0x00` |      4 | `0x0C`, constant in 65/65                                   |
| `0x04` |      4 | offset of the first large section (`0x1B00C` in `BPLD012`)  |
| `0x08` |      4 | offset of the second large section (`0x3600C` in `BPLD012`) |
| `0x0C` |      4 | offset-table entry count, 16 in 65/65                       |
| `0x10` | 4 each | 16 section offset-table offsets                             |

Both section offsets are 4-byte aligned in 65/65, but not 16-byte aligned and not constant across
characters (section 1 starts between `0xE780` and `0x306F4`; section 2 between `0x21EEC` and
`0x51B60`). Section-2 minus section-1 is `0x1B000` in 41 entries and `0xF8D0`-`0x306E8` elsewhere;
bytes after section 2 are `0x1B000` in the same 41 entries and `0x2E14`-`0x306E8` elsewhere. The
blob is `[header][section 1][section 2][trailing region]`; in 41 of 65 entries every region is a
whole number of 4,096-byte pages.

The two large sections are the compressed character-sprite blobs: `BPLCHAR` loads the decoded blob
at `0x8003B80C`, `PLCHAR` at `0x801CE400`. The consumer of the header table is not located, so the
table's semantics beyond its shape stay unproven and the section content is not decoded.
